# Sheet schema conventions (KS-53)

**Status**: Adopted. Applies to every entity tab in the Sheets datastore,
present (`rooms`) and future (`tenants`, `leases`, `bills`, `meter_readings`,
`assets`). Built on [0001](decisions/0001-sheets-over-postgres.md) and the
[KS-52 spike findings](data-layer.md).

**Why this exists**: the sheet is admin-editable by design — that's the whole
point of choosing Sheets over Postgres. But a shape with no enforced identity
or contract can silently corrupt on an ordinary human edit, and nothing about
Sheets will tell you when it does. The rules below are what keeps that
editability from breaking the app underneath it.

## The evidence, not just the argument

This isn't hypothetical. Two things happened this cycle, on the real
`KS_Mansion_DB` sheet, while populating it by hand for KS-7:

- **A manual paste silently duplicated every row** — `room_number` values
  each appeared twice. Caught only by reading the sheet back and counting.
> ⚠️ **Correction (2026-08-25):** the second bullet below originally claimed
> `KS_Mansion_DB` was *currently* exhibiting column-shift corruption. **That
> was wrong, and the production data is fine.** Re-reading the sheet as a
> table shows all 27 rows well-formed across 7 columns with blanks correctly
> preserved (`101 | unit | occupied | 2636 | | AC | TRUE`). The earlier
> reading came from a search-result snippet that collapses empty cells — a
> rendering artifact of that tool, not the sheet. The example is kept below
> because it is still an accurate illustration of *what the failure looks
> like*, and the read-time validation it motivated is still worth having; but
> it is a constructed example, not an observed incident. The row-duplication
> incident recorded above **did** happen and is unaffected by this
> correction.

- **What a column shift would look like** — the shape this document exists to
  prevent, illustrated with the snippet that was originally misread as real:

  ```
  room_number,kind,status,price,detail,type,hasMeter
  101,unit,occupied,2636,AC
  206,unit,occupied,AC
  laundry,common,occupied,3192,ร้านซักผ้า
  ```

  Room 101's row has 5 values for a 7-column header — `AC` (the `type`) has
  shifted left into where `detail` and `hasMeter` should be, because the
  empty cells between them were dropped instead of preserved. Room 206 (a
  room with no recorded rent — expected, see KS-7) shows the same shift one
  column earlier: `AC` lands in the `price` slot. Nothing errored. A
  positional reader (`row[3]` = price) would silently read `"AC"` as a price
  for 206 and `"ร้านซักผ้า"` as a `price` for the laundry.

  **This shape is not hypothetical even though this instance was not real.**
  The Sheets API genuinely omits trailing empty cells, so rows arrive ragged
  by design — `createGoogleSheetsClient` normalises that, and the repository
  resolves cells by header name rather than position precisely so a short or
  shifted row cannot be silently misread.

## Rules

### 1. One tab per entity

`rooms`, `tenants`, `leases`, `bills`, `meter_readings`, `assets`. No tab
holds more than one entity type, and no entity's rows are split across tabs.

### 2. The header row is the schema contract — read by name, not position

Every repository implementation reads the header row first and resolves
columns by **name**, building a name→index map, before reading any data row.
Never assume column N is always the price column. Admins can and do insert
or reorder columns (`type`, `status` already exist in `KS_Mansion_DB` ahead
of the console's own model — see below); a positional reader breaks the
first time that happens, silently, in exactly the shape shown above.

### 3. Every row has a stable ID column — separate from any human-facing field

Never address a record by row index; inserting or sorting a row would
silently repoint every reference to it. IDs are generated by the app on
write, once, and never recomputed from other fields at read time.

**This is a separate column even when its value looks redundant with a
human-facing one.** `KS_Mansion_DB` now carries an explicit `id` on every tab,
seeded for rooms from the existing `room_number` values — so the two columns
hold the same string today. That is fine as a *value*; what matters is that no
code relies on `id === label` holding. A tenant's name can change (typo fix,
marriage); a lease has no natural human label at all. Codifying "id happens to
equal the display field" as normal is exactly how that assumption leaks into
an entity where it silently breaks later — the same failure class rule 5 names
directly.

The in-memory `Room` model gets this right structurally —
[`src/lib/models/room.ts`](../src/lib/models/room.ts) keeps `id` and `label`
as distinct fields, even though
[`memory-room-repository.ts`](../src/lib/repositories/memory/memory-room-repository.ts)
sets `id: label` for every seed room. The Sheets adapter reads an explicit
`id` cell and never derives one from `room_number` or `label` at read time.

### 4. Foreign keys by ID, never by room number or tenant name

A lease references `room_id` and `tenant_id`, not `"101"` or a tenant's
printed name. Both of those change or collide in ways an opaque ID doesn't.

### 5. Reserved/computed columns are marked, so nobody hand-edits what the console owns

> Per-column ownership for the `rooms` tab, and the sheet-side protections
> that enforce it, are in [admin-collaboration.md](admin-collaboration.md)
> (KS-56).

Any column the console derives or overwrites on write (e.g. a computed
`archived` flag, a future `balance`) gets a documented prefix or a listed
callout in that tab's section of this doc, so an admin editing the sheet
directly can tell "data I own" from "output the console owns."

### 6. Append-only where it matters

`bills` and `meter_readings` are history, not current state. A correction is
a new row, not an edit to an old one. This directly shapes KS-18 (meter
entry): a corrected reading should append, not overwrite — worth having this
rule on record before KS-18's persistence design gets improvised ad hoc.
`rooms`, `tenants`, and `leases` are current-state entities and may be
edited in place (subject to rule 7 for removal).

### 7. Soft delete, not hard delete

Deleted rows get an `archived` flag (or `status`), not row removal. A hard
delete in a shared, human-editable sheet is unrecoverable in practice —
there's no trash to restore from the way there is for a single file.

## Validate on read

Given the demonstrated failure mode above, every repository implementation
reading a tab should check, before trusting the data:

- Row count matches the tab's non-header row count (no silently-skipped
  trailing rows, no double-read header).
- The ID column has no duplicate, no blank values.
- Every row has a value in every column that *requires* one — see the
  columns/identity split below, since not every contracted column carries a
  value on every real row. A row short of the cells its contract demands is
  exactly the corruption shown above and should be flagged, not silently
  shifted.

This is a repository-implementation concern (KS-2/KS-54's Sheets adapter),
not a schema-doc deliverable — noted here so it isn't designed ad hoc later.

## Contracted headers, and what makes a row a record

Each repository declares two things, not one (`TabContract` in
[`tab-reader.ts`](../src/lib/repositories/sheets/tab-reader.ts)):

- **`columns`** — every name that must appear in the header row. A missing
  one fails the whole tab by name.
- **`identity`** — the subset that makes a row a *record*. A row empty in all
  of them is a blank or a divider and is skipped.

They started as one list and had to be split. Several columns hold no value on
plenty of real rows — `note`, `occupation`, most of the address parts — so
demanding a value there rejects legitimate tenants; but leaving them
unverified means a header typo (`occupatoin`) reads as empty for every tenant,
forever, silently. Both lists close both holes.

### `rooms`

```
id, room_number, kind, status, rent_rate, detail, type, floor, hasMeter, has_tv, has_fridge, has_aircon
```

Identity: all of the above except `detail` and `type`.

- **`rent_rate` is rent, not a month's bill.** It was called `price` and was
  populated from the `ค่าห้องฯ` column of แบบฟอร์มเก็บเงินค่าห้อง, which is a
  *total* — rent + water + electricity — and therefore moves every month.
  Room 101 read 2,636 where its rent is 2,200 (2,200 + 336 ไฟ + 100 น้ำ),
  verified against ใบแจ้งค่าห้องพัก. The column was renamed along with the
  correction so the header says what it holds.
- **Values arrive formatted.** The API returns the *formatted* value, so a
  number-formatted column reads as `"2,200"`. Numeric parsing strips
  separators centrally in `tab-reader.ts`; nothing should re-implement it.
- `rent_rate` maps to `rentRate: number | null`. A blank cell means no rate is
  recorded — not zero, and not a guess (KS-1/KS-7's "don't invent data").
- **`status`** is now modelled: `occupied`, `noticeGiven`, `available`,
  `maintenance`. `noticeGiven` is แจ้งออก — a real state between occupied and
  vacant, in which the room is billed **utilities only, no rent**. That is the
  `Utility` value in the monthly report's `จะได้รับ ณ สิ้นเดือน` column, and a
  boolean occupied/vacant cannot express it.
- **`has_tv` / `has_fridge` / `has_aircon`** feed the month-end report, which
  prints TV / ตู้เย็น / แอร์ with per-floor totals. A blank reads as **"not on
  file", which is a third state distinct from `false`** — "nobody filled this
  in" and "this room has no fridge" are different facts and only one belongs
  on a report. Blank is allowed rather than fatal because nothing records TV
  or fridge today, and failing the tab until 54 cells were invented would have
  been the "don't invent data" ruling turned upside down. Fill them when the
  report needs them; until then `null` is the honest value.

  `hasMeter` deliberately keeps rejecting a blank. The asymmetry is the point:
  an unrecorded meter drops a room out of the meter round, where an unrecorded
  fridge costs nothing until a report exists to print it.
- **`type` (AC/FAN) now overlaps `has_aircon`** and stays admin bookkeeping.
  Two cells that can disagree about the same fact is the corruption class this
  document exists to prevent — retire `type`, or keep it explicitly as a
  marketing label and treat `has_aircon` as the one the console reads.
- `label` (the display name) comes from `detail` when populated, falling back
  to `room_number` — units carry no `detail` (their number already is the
  label) and the common spaces carry their Thai name there, with
  `room_number` holding the English slug `laundry` / `undercroft`.

### `tenants`

```
id, full_name, nickname, id_card_last4, phone, occupation, evaluation_grade, note,
address_house_no, address_road, address_subdistrict, address_district, address_province, address_postcode
```

Identity: `id`, `full_name`.

- **The address is six columns, not one.** `สัญญาเช่าห้องชุด` has a separate
  blank for each part, so contract generation (KS-31) cannot fill them from a
  single line, and splitting one heuristically at generation time would be
  guesswork on a legal document. A sparse address is normal and renders with
  the missing parts omitted rather than as bare `ถ. ต. อ.` prefixes.
- **`id_card_last4` holds four digits, never the full 13.** The sheet is
  opened directly by admins, so anything here is visible to everyone with
  access. A longer value fails the row instead of being truncated — silently
  trimming would hide that a national ID had been pasted in.
- `evaluation_grade` is `A` / `B` / `C` per the source sheet's own legend
  (ดีมาก / ดี / พอใช้ได้). Blank means not yet assessed, which is a real state
  for someone who moved in this week — not a failing grade.
- `occupation` is free text on purpose: real values are compound
  (`ราชภัฏ/7-11`, `ซีนิค/นักเรียน`), so a fixed list would lose information.

### `leases`

```
id, room_id, tenant_id, start_date, end_date, signed_date,
rent_rate, deposit, advance_rent, occupant_count, end_reason, previous_lease_id
```

Identity: `id`, `room_id`, `tenant_id`, `start_date`.

- **Dates are Thai Buddhist-era text** (`1 มี.ค. 2568` or `1/3/2568`), in a
  column formatted as **plain text**. See `sheets-lease-repository.ts` for why,
  and [admin-collaboration.md](admin-collaboration.md) for the formatting trap.
- **`signed_date` is not `start_date`.** วันที่ทำสัญญา is the contract header
  date; a tenancy is often signed before it begins.
- **`occupant_count` is a billing input**, not a note: ค่าน้ำ is occupants ×
  100. A blank fails the row rather than defaulting — the source spreadsheet's
  own instruction is that leaving it out makes the calculation wrong
  ("หากไม่กรอกจะคำนวนผิดพลาด"), and a plausible-looking wrong bill is worse
  than no bill. Zero is accepted: ร้านซักผ้า is a shop on its own water meter.
- **`end_reason`** is `normal` or `absconded` (`( หนี )` in
  บัญชีแจ้งคนเข้า-ออก, common enough there to be a normal outcome). Setting it
  without an `end_date` fails the row — a lease cannot have ended in a
  particular way and still be running.
- **`previous_lease_id`** links a room transfer (ย้ายห้อง) to the tenancy it
  continues. These are usually the same tenant, so without the link one long
  tenancy reads as two short ones and the length-of-stay analytics (AC-5.2)
  are wrong.
- `rent_rate` here is **the rate this tenancy is billed at**, which is not
  necessarily the room's current rate. Billing must read the lease, or a rate
  change would silently re-price every sitting tenant.

## Pending sheet migration

The code on this branch reads the headers above. `KS_Mansion_DB` does not
carry all of them yet, and **a missing column fails the whole tab by name** —
deliberately, so a half-migrated sheet cannot be half-read. That means this
branch must not be deployed until the columns exist.

**Column order does not matter** — every column is resolved by name, so
**append** new columns at the far right rather than inserting them. Nothing
existing moves, which removes the column-shift risk from the migration
entirely.

**`rooms`** — rename `price` back to `rent_rate`, then append three empty
columns:

| Column | Values | Notes |
|---|---|---|
| `has_tv` | `TRUE` / `FALSE` / blank | Blank means "not on file"; leave empty for now |
| `has_fridge` | `TRUE` / `FALSE` / blank | Same |
| `has_aircon` | `TRUE` / `FALSE` / blank | Optionally seed from `type`: `=IF(G2="AC",TRUE,FALSE)`, then paste as values |

`status` already exists and its values (`occupied`, `maintenance`,
`available`) are already what the console reads. `noticeGiven` is the fourth
accepted value — set it for a room that has given แจ้งออก, and back to
`occupied` when it is re-let.

**`tenants`** — replace `address` with six columns and add three more:

```
occupation, evaluation_grade, note,
address_house_no, address_road, address_subdistrict,
address_district, address_province, address_postcode
```

Split the existing `address` value across the new parts by hand; the console
will not do it, because guessing where a one-line address divides is exactly
the kind of inference that would end up printed on a lease contract.

**`leases`** — add four columns:

```
signed_date, occupant_count, end_reason, previous_lease_id
```

`occupant_count` must be filled for every existing lease row. `signed_date`,
`end_reason` and `previous_lease_id` may be left blank.

**One data correction, separate from the columns:** the `rent_rate` on lease
`l-001` reads `2636`, which is the old month-total figure. Room 101's rent is
`2200`.
